# PROD：派車照採購單數量——叫貨後才取消的件數照派原店（2026-10）

> **狀態：⛔ 尚未執行。** 這個資料夾放的是上正式庫要用的「確認」「一鍵關掉」「還原」，由老闆本人貼進 Supabase SQL Editor。沒有任何自動流程會跑這些檔。
>
> 改動本體是 `supabase/migrations/20261016000000_picking_post_po_cancel_to_store.sql`（以下叫 migration）。

## 這次改了什麼

- 叫貨（採購單成立）之後才被取消的件數，派貨工作台照樣算給原本那家店（貨到店後多的自動進該店【內部】，月結照算）。停用的店不帶，那幾件留給總倉決定。
- 只對「上線那天起才成立」的採購單品項套用；之前的採購單一個數字都不變。
- 同一團、同一樣商品掛兩張以上採購單的，不套（照 #1082 的紅字＋撿貨草稿留 0）。
- 叫貨後取消過、又被「復原取消」的訂單，之後再取消一律照今天留總倉（取消時間會被蓋掉，分不出第一次取消在叫貨前還是後；寧可少派、不多派）。
- 採購單頁「分店／批發追加」：叫貨後取消的件數不再拿去抵。請購單加的件數跟以前一樣；採購單（只限套新規則的）改成「加完＝現在有效的需求＋叫貨後取消照派的件數」，不會往下減。
  - ⚠️ 這樣算，採購單**可能比請購單加得少**：例如以前追加時已經多加過、之後那張取消的單又被復原；或叫貨後取消的是抵減單（負數量）。
- 另外多三支只讀查詢，給之後的畫面用（取消前提醒、分店追加預估、派貨工作台的提示字）；畫面這次還沒改。
  - 派貨工作台那支（`rpc_picking_post_po_cancelled_by_sku`）只回自己公司的、只到「採購單品項 × 店」；兩張內部的表（`v_picking_po_rule_items`、`v_picking_post_po_cancelled`）前端不能直接讀。

## 順序

0. **CEO 先改上線日**：migration 裡 `_picking_po_rule_cutover()` 那一行（有「⚠️ 上線日」註解）改成實際上線當天 00:00（台北）。只改這一行。
1. **貼 migration**。最前面有前置檢查：正式庫的派貨表、建撿貨單、分店追加如果不是 10/15 核對時那一版，或依賴的東西被改過，會直接停下、一行都不改。整份貼兩次也沒關係。
   - 中途斷線、或某一句出錯：每一組改動（建立＋說明＋權限）各自一個小交易，斷在中間那一組會整組退回；CEO 看過截圖、說可以重貼之後，**整份重貼一次**就會接著做完，結果跟一次貼完一樣。
   - ⚠️ **貼到一半跳出紅字（報錯）時，照這三步：**
     1. **先截圖給 CEO**（整個畫面、紅字要看得到），**先不要重貼**，檔案裡的字也一個都不要改。
     2. CEO 說可以重貼時，**先開一個新的查詢分頁**（SQL Editor 裡按「＋」或「New query」新增一個查詢），在新分頁裡整份貼上再按 Run。**不要在剛剛報錯的那個分頁直接重貼。**
     3. 為什麼要換分頁：如果錯誤發生在某一組小交易裡、而且同一個分頁還沒收尾，這個分頁可能停在中止狀態（已經失敗、還沒收尾）；在同一個分頁接著貼，可能被它卡住，後面每一句都跳 `current transaction is aborted` 之類的紅字，看起來像檔案壞了，其實是那個分頁卡住。換新分頁就避開它。前面已經做完的組不會因為這次報錯被退回，重貼會自己接著做。
     - 新分頁重貼還是一直跳 `current transaction is aborted`：一樣截圖給 CEO，不要自己一直重按。
2. **貼 `postcheck_readonly.sql`**，最後一列「總結」要 ✅。
   - 第 14 列「舊數字不變」：把派貨表用改前的算法再算一次逐列比，差異只能出現在套新規則的採購單品項（上線當天通常 0 筆）。
   - 第 8 列如果是 ⚠️：只是資料庫版本的印法不同，內容對，不算錯。
   - 第 11～13 列是權限：兩張內部的表前端不能直接讀、三支查詢只給登入後台的人、分界時間只給登入後台的人。
   - 第 14、15 列會把派貨表算兩次（跟打開兩次派貨工作台差不多重），請挑沒人在派貨、收貨的時候跑。
3. **前端（另一批）合併之前**：工作台已經會照派原店（格子會自動解開、預設帶數），只是還沒有提示字和取消提醒。
   - 反過來先合併前端的話，提醒查詢還不存在，每次取消都會跳「無法確認是否已叫貨」，很煩，所以一定先貼 SQL。

## 出問題時

- **只想先停用**：貼 `kill_switch_20261016000000.sql`。要再打開：重貼一次 migration（上線日回到檔案裡寫的那天）。
- **整個還原**：貼 `rollback_20261016000000.sql`。最前面一樣有前置檢查，現況不是「本檔新版」也不是「改前那一版」就停下。三支改過的連權限也照原檔再給一次（派貨表給登入後台的人讀、建撿貨單與分店追加給登入後台的人執行）。
- ⚠️ 不要直接重貼 `20260816000050`、`20260818000030`、`20260908000000`、`20261002000000`：會把這次改的那支蓋回去（確認查詢會變 ❌）。

## 危險（兩邊都講）

- **貼了會怎樣**：叫貨後才取消的件數會派到原本那家店，門市要自己消化（多的進【內部】、月結照算）；總倉不再莫名多貨。算錯的話只影響「叫貨後取消」那幾件（多派到原店、或照今天留總倉），其他商品數字不變；分店追加算錯＝採購單多叫或少叫幾件。
  抵減單在叫貨後被取消、之後又分店追加：採購單會比請購單少（少的那幾件＝那張抵減單的數量），請購單上那幾件不會跟廠商叫。有一鍵關掉可以馬上回到今天的行為。
- **不貼會怎樣**：每次叫貨後有人取消，貨就留在總倉、沒有提醒，食品可能放到過期。
- **已知做不到（照今天）**：叫貨後新開的單、加在既有品項上的量、叫貨後改少數量；同一團兩張以上採購單；請購草稿到轉採購之間取消的；叫貨後取消過又復原、之後再取消的（少派：那幾件留總倉）。
- **沒登入的帳號（anon）**：分界時間收回了沒登入的執行權限，所以沒登入的人就算有派貨表的讀取權限也讀不出來（確認查詢第 17 列會寫現況）。登入後台的人不受影響。
- **程式碼紀錄的注意事項**：派貨表與建撿貨單是以正式庫那一版為底重建的，**沒有**包含 `20260908000000`（#917「短撿只扣實撿」）；#917 要上請另案、以本檔為底。

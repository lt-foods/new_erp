# PROD：撿貨用檢查表——同一團、同一樣商品掛了兩張以上採購單（2026-10）

> **狀態：⛔ 尚未執行。** 這個資料夾放的是上正式庫要用的「確認」與「還原」，由老闆本人貼進 Supabase SQL Editor。沒有任何自動流程會跑這些檔。
>
> 改動本體是 `supabase/migrations/20261015000000_picking_multi_po_campaigns.sql`：**只新增一支只讀的檢查表（view）**，不動任何資料表、任何一筆資料、任何既有的 view 或函式。

## 這次改了什麼

- 同一團、同一樣商品如果掛了兩張以上採購單，派貨需求會被每張採購單各算一次（變兩倍），先來後到分貨就會派錯店。
- 新增的檢查表列出「哪一樣商品、在哪一團、掛了哪幾張採購單」，給前端用：
  - 撿貨草稿：這種商品各店數量全部留 0，紅字寫出團號與採購單號，請人照訂單樞紐填。
  - 派貨工作台：這種商品加紅字，數字照舊。
  - 請購單頁的補單預覽：會多開一張採購單的那幾列標紅，要先勾「我知道」才能按確認。

## 順序

1. **先貼 migration**（`supabase/migrations/20261015000000_picking_multi_po_campaigns.sql`）。最前面有前置檢查，缺東西會直接停，一行都不會改；整份貼兩次也沒關係。
2. **貼 `postcheck_readonly.sql`**，最後一列「總結」要是 ✅。
   - 第 5 列查的是 10/13 那一樣（G02671-01／GRP-20260914-056）。如果那團的訂單或採購單後來被改過，這一列可能會變 ❌，那時請先找工程師看，不一定是貼錯。
   - 第 8 列確認「所有人共用的 PUBLIC」讀不到，只有登入後台的人讀得到。
   - 第 6、7 列只是數字：第 7 列＝「現在加進撿貨草稿會被全部留 0 的商品」有幾樣、是哪幾樣。
   - 第 6、7 列會把檢查表與派貨工作台那張需求表各算一次（第 7 列跟打開一次派貨工作台一樣重），請避開派貨、收貨的尖峰時段。
3. **全部 ✅ 之後才合併前端。**
   - 反過來的話，前端讀不到檢查表，撿貨草稿每一樣「有需求」的商品都會走「多張採購單檢查失敗、各店全部 0」：草稿還能用，但每樣都要手填。
   - 本來就沒有需求的商品（需求表上一列都沒有）不會標「檢查失敗」：它本來就帶不出任何數字，標了只會多一句嚇人的紅字。

## 已知限制（這次不處理）

- **補貨申請的需求擋不到（改前就有，這次不擋，另案處理）**：檢查表只看「團的訂單」。
  - 補貨申請的明細本身不會重複（同一張補貨單、同一樣商品只能有一列），但它連到的請購單裡，同一樣商品可能有兩列、各自轉成不同的採購單品項。這時派貨需求會把補貨量算兩次，這次的檢查不會擋、不會標紅字。
  - 請購單裡同一樣商品有兩列，系統本來就沒有擋（沒有唯一限制），所以不能當成「很少見」。
  - 這不是這次改出來的：改之前就是這樣，這次的修改沒有讓它變好或變壞。
- **檢查表讀不到、但商品本來就沒有需求**：不標「檢查失敗」（理由見上面「順序」第 3 點）。

## 危險（兩邊都講）

- **貼了會怎樣**：只多一支只讀的檢查表，不會改到任何帳或訂單。前端合併以後，遇到「同一團兩張採購單」的商品，撿貨草稿不再自動帶數字，要人照訂單樞紐填，會多花一點時間。
  - 檢查表算錯有兩種：漏擋（跟現在一樣會派錯）、誤擋（正常商品也要手填，不會派錯，只是麻煩）。
- **不貼會怎樣**：前端合併後，每一樣有需求的商品都被當成「檢查失敗」，每樣都要手填（本來就沒需求的商品不受影響）；不合併前端的話，跟現在一樣會把兩張採購單的需求算兩倍。
- **還原（rollback）會怎樣**：只拿掉檢查表。前端已經上線的話，撿貨草稿每一樣有需求的商品都變成「檢查失敗、全部 0」，派貨工作台最上面多一行紅字，其他功能照常；要恢復就重貼 migration。

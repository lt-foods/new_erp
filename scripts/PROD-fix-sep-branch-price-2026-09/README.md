# PROD-fix：九月分店價錯價修正（2026-09）

> **狀態：⛔ 尚未執行。這個資料夾只是「留紀錄」，讓大家看得到要做什麼、怎麼做、怎麼還原。**
> 要不要執行、什麼時候執行，由老闆決定，並且由老闆本人貼進 Supabase SQL Editor。沒有任何自動流程會跑這些檔。
>
> 🔴 這些檔**刻意不放在 `supabase/migrations/`**，因為那個資料夾的檔案會被當成結構變更套用到正式庫。
> 這裡照 `scripts/PROD-fix-*.sql` 的既有慣例放一次性的正式庫資料修正。

## 做什麼、為什麼

- 2026 年 9 月有一批商品的「分店價」打錯，共 57 個品號，正確價以老闆的 Excel 為準。
- 九月的月結和店家每日對帳，都是照「派車那一刻」查到的分店價算錢。所以這批錯價讓九月草稿月結上的金額也跟著錯。
- 修正分兩件事，放在同一個交易裡做：
  1. 把這 57 個品號的分店價，從 2026-09-01 00:00（台北時間）起改成正確價。
     - 一般商品：用系統的改價函式 `rpc_upsert_price`。
     - 9/1 之後已經另開過新版本的 3 個品號：先刪掉那個新版本（原樣留在備份裡），再用改價函式從 9/1 起重開。
  2. 重新產生 2026 年 9 月的月結草稿。
- 八月的帳不受影響。修正檔會逐筆比對八月每一筆帳的時間、數量、價格，只要有任何一筆變了，就整筆取消。

## 需要老闆親自做的事

- **2 修正**：檔案最上面的兩個參數要老闆親自填。
  - 操作人 UUID：用 0-D 找到的老闆本人 UUID。
  - 要作廢的人工調整 ID：老闆已裁定一筆都不作廢，維持空的即可。
- **貼的時機**：2 和 4 都會把月結、價格、派車相關的表短暫鎖住，而且採「拿不到鎖就立刻放棄」。請挑沒人在後台操作、倉庫沒在派車收貨的時候貼。看到「有人正在使用」就過幾分鐘再貼。

## 還原方式

- 貼 `4_restore_WRITES.sql`。
- 它會先確認「修正之後沒有任何人再動過」這些資料：價格、月結、調整、爭議，以及九月的派車、收貨、退貨、店轉店。
  - **都沒動過**：把資料逐欄換回備份，最後再驗算一次，確認完全相同。
  - **只要有一筆被動過**：它會停下，什麼都不改，改成人工對帳。這樣做是為了不把別人的新資料蓋掉。
- 實務上，修正之後只要九月又有新派車，自動還原就會被擋下。

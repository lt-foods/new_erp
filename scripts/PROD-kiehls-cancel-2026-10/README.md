# 契爾氏化妝水叫錯款式：25 筆客人品項一次取消（2026-10）

> **狀態：⛔ 這個資料夾是「留紀錄」。** 要不要貼、什麼時候貼，由老闆決定，由老闆本人貼進 Supabase SQL Editor。沒有任何自動流程會跑這些檔。
>
> 刻意**不放在 `supabase/migrations/`**（那裡的檔會被當成結構變更）。照 `scripts/PROD-fix-*` 的既有慣例，放一次性的正式資料修正。
>
> ⛔ 阿審（Codex）審過、問題清空之前不要貼。

## 這是在處理什麼

- 商品：契爾氏 kiehl's 金盞花植物精華化妝水 40ml（G02596-01），團 GRP-20260910-027。
- 叫貨時叫錯款式，錯的 33 件 10/19 已經派到 9 家店；廠商說正確的沒貨 ⇒ 訂這個商品的客人都拿不到。
- 系統的「斷貨」鈕按不了（只給還沒全到貨的採購單），店家的「刪除品項」也刪不了（大多是已確認、出貨中的單）。
- 老闆 10/21 決定：用一份 SQL 一次取消。10/21 早上查是 27 筆（33 件）；**松山那 1 筆老闆中午已經在後台手動「刪除品項」**（那張單只有這一項，整單已一併取消），另外 **南平 1 張（3 件）店家 10/21～22 已經按了後台「取消訂單」**：那個鈕只把整張單改成已取消、不改品項，所以品項還顯示等貨中；業務上已經取消，這份**不動它、不發通知給它**（01／04 會列在「不在範圍」）。所以這份處理的是剩下的 **25 筆（29 件）**。

## 檔案與順序

| 順序 | 檔 | 會不會改資料 | 做什麼 |
|---|---|---|---|
| 1 | `01_預覽_唯讀.sql` | 只看不改 | 列出會被取消的 25 筆（門市、訂單號、狀態、件數）、哪些單會整張取消、哪些付過錢不會動；最後一段列出總部帳號，給老闆認自己的那一個 |
| 2 | `02_取消25筆.sql` | **✅ 會改** | 取消 25 筆；只剩這一項的單整張取消；寫編輯歷史。**最上面要填操作人（老闆本人那串 UUID）**，CEO 會在老闆確認後填好 |
| 3 | `04_貼完確認_唯讀.sql` | 只看不改 | 每一列 ✅ 或 ❌，確認 02 做對了 |
| （可選） | `03_通知客人_可選.sql` | **✅ 會新增通知** | 在會員 App「通知」頁對這些客人各留一則「商品斷貨通知」。要不要發由老闆決定；一定要在 02 之後 |
| （備用） | `05_還原_備用.sql` | **✅ 會改** | 萬一要撤回 02，把品項與整單取消的單還原成 02 之前的樣子。平常不用貼 |

**貼法：01 → 02 → 04。** 03 看老闆要不要發（貼完 03 再貼一次 04，看「通知」那一列）。

**01 有任何一列 ❌，就先不要貼 02／03**，截圖給 CEO（例如正式系統少了某個觸發器、會整單取消的單以前就取消過）。

## 老闆貼的時候要注意

- **一次貼一整份**：打開檔案、全選、複製、貼進 SQL Editor、按執行。不要只貼一段。
- **看到紅字（ERROR）**：先截圖給 CEO，**⛔ 不要重貼**。
  - 紅字開頭是【停】：什麼都沒改，紅字會寫是哪一項不對。
  - 紅字寫「有人正在操作」或 lock timeout：什麼都沒改，過幾分鐘再貼一次；連續兩三次都這樣再截圖。
- 02、03、05 貼完，Supabase 可能只顯示「Success. No rows returned」—— 這是正常的（白話總結不一定顯示出來），接著貼 04 看結果。
- 02 不小心貼了兩次也沒關係：第二次會認出「已經做過」，什麼都不改。
- 03 不小心貼了兩次、或兩個視窗同時貼也沒關係：第二次會等第一次做完，再顯示「已經發過」，一則都不多發。只有「一部分客人收到、一部分沒收到」這種怪情況會紅字【停】，那時截圖給 CEO，不要自己補發。

## 做了會怎樣／不做會怎樣

- **做了**：
  - 這 25 筆客人品項變成「已取消」並標「斷貨」。只有這一項的單整張取消、單頭也標「斷貨」（照平常斷貨的做法）：客人 App 會看到那張單寫「⛔ 供應商斷貨，本筆訂單已取消」。收尾成已完成、單子留著、付過錢的單，單頭不標。
  - 之後還沒收貨的 4 家店（中和、古華、文山、永和）收這批錯貨時，不會再因為這批貨把這些客人推成「可取貨」。
  - ⚠ 單上**還有別的商品**的客人，單子會留著、只少這一項。這種單如果是「出貨中」，店家收這批錯貨時客人仍可能收到一則「您的商品到貨」推播（系統原本就這樣，這次沒改）。01 會列出有幾張。
  - ⚠ **付過錢／用過儲值金**的單：只取消這一項，單子不動、**不會自動退錢**，要人工處理。01 會列出來（預期 0 張）。
- **不做**：客人訂單一直掛著「等貨」；4 家還沒收貨的店收貨時，客人可能收到到貨通知、來了拿到錯的款。

## 不會動到的

派車單、庫存、採購單、月結、店家退回總倉的單、開團商品設定。（客人品項如果有「從店內庫存配過貨」，會先把那個配貨還回去 —— 跟店家刪除品項一樣；預期 0 筆，01 會列出。）

## 會員通知（03）會不會推 LINE

不會。這份只在會員 App 的「通知」頁留一則（跟平常按斷貨發的那則一模一樣）。程式碼紀錄裡通知表沒有任何觸發器；正式系統實際有沒有，01 第⑤段會查給你看（那一列要是 ✅）。發出去就收不回來。

## 萬一要撤回（05）

- 只有 02 之後**沒人再動過**這 25 筆、以及它們所在的每一張單（包括單子留著、付過錢、沒被 02 改單頭的那幾張，和單上其他商品）時才會還原；有人動過（收貨、取貨、改單、取消…）就【停】、什麼都不改，改人工處理。
- 還原不了的（05 結尾那行也會寫出來）：
  - 02 還回去的「店內庫存配貨」（要店家重新配）。
  - 02 整單取消時，系統會順便把「同一張減抵單上、其他早就取消的訂單」還掛著的配貨一起放掉；那也不會復原（只影響本來就該放掉的殘留）。
  - 03 發出去的通知（收不回來）。
  - 這些品項、訂單的「最後修改人、修改時間」會變成還原的那個人和時間。
  - 02 之後如果店家已經把錯貨收進來，還原回「出貨中」的單不會自己變可取貨。
- 05 只還原 02 做的；松山那筆是老闆手動刪的，05 不會碰它。
- 後台訂單頁的「復原取消」鈕救不回這批：整單取消的單頭有斷貨標記，鈕不會出現；就算硬叫，系統也會擋下並叫人去採購單按「回復斷貨」—— 那顆鈕對這批無效（這批沒有斷貨單）。要撤回只能用 05。
- 05 會把 02 蓋的單頭斷貨標記一起清掉（02 之前就有的不動）。

# 限量團超賣：三團一次取消 73 張超賣訂單（2026-10-28）

> **狀態：⛔ 這個資料夾是「留紀錄」。** 要不要貼、什麼時候貼，由老闆決定，由老闆本人貼進 Supabase SQL Editor。沒有任何自動流程會跑這些檔。
>
> 刻意**不放在 `supabase/migrations/`**（那裡的檔會被當成結構變更）。照 `scripts/PROD-*` 的既有慣例，放一次性的正式資料修正。
>
> ⛔ 阿審（Codex）審過、問題清空之前不要貼。

## 這是在處理什麼

三個限量團被記事本留言、後台加單賣超過上限（商城下單一張都沒超過）。老闆決定把超出的訂單整張取消，不要一張一張按。

| 團 | 上限 | 取消 | 保留 |
|---|---|---|---|
| 洗面乳 GRP-20261015-024 | 6 | 0006～0046、INT0047（湖口內部單）＝ **42 張** | 0001～0005（5 件） |
| 辣椒醬 GRP-20261016-048 | 34 | 0027～0039、0041～0043、TF0001（經國，轉單轉進來的）＝ **17 張** | 0001～0026（34 件） |
| 微燻李 GRP-20261021-018 | 22 | 0018～0031 ＝ **14 張** | 0001～0017（21 件） |

- 合計 **73 張**（42＋17＋14）。⚠ 需求單寫 72 張，是加總時少算一張；各團的名單本身沒變。
- 另外辣椒醬 **0040** 也會被取消（不算在 73 張裡）：TF0001 就是 0040 整張轉出去的。取消 TF0001 時系統會自動把 0040 救回來（等於超賣的那張又活回來），所以 02 接著把 0040 也取消。
- 0006 古華（6 件）、0018 忠順（2 件）各有 1 件原本在上限內，照老闆決定**整張取消**，所以 02 做完是 **5／34／21 件**；老闆之後用後台加單各補 1 件，才會是 6／34／22。

**做法**：02 逐張呼叫後台訂單頁紅色「取消」鈕背後同一支程式，效果等於老闆一張一張按。不另外寫取消規則。

**貼法：01 → 02 → 04。**

**01 有任何一列 ❌，就先不要貼 02**，截圖給 CEO。

## 老闆貼的時候要注意

- **一次貼一整份**：打開檔案、全選、複製、貼進 SQL Editor、按執行。不要只貼一段。
- **看到紅字（ERROR）**：先截圖給 CEO，**⛔ 不要重貼**。
  - 紅字開頭是【停】：什麼都沒改，紅字會寫是哪一項不對。
  - 紅字寫「有人正在操作」或 lock timeout：什麼都沒改，過幾分鐘再貼一次；連續兩三次都這樣再截圖。
- 02、05 貼完，Supabase 可能只顯示「Success. No rows returned」—— 正常，接著貼 04 看結果。
- 02 不小心貼了兩次也沒關係：第二次會認出「已經做過」，什麼都不改。之前已經有人手動按掉幾張的，也會自動跳過。

## 做了會怎樣／不做會怎樣

- **做了**：
  - 這 73 張＋0040 變成「已取消」，三團的已賣數量回到上限以內（5／34／21）。商城、後台加單、請購單同步、派貨需求算數量時都會把它們排除。
  - **用了儲值金的單會自動退回會員餘額**（取消鈕本來就會做）；01 第③段會列出幾張、多少錢。
  - ⚠ 品項會顯示還在「等貨中」—— 取消鈕本來就只改整張單、不改品項，跟老闆手按一模一樣；系統算數量的地方都看整張單的狀態，不會算進去。
  - ⚠ 被取消的客人**不會收到任何通知**（取消鈕本來就不發），要不要另外跟客人說由老闆決定。
- **不做**：三團的已賣數量一直超過上限，總倉會照超賣的數量叫貨、派貨，到時候廠商給不出來或貨不夠分。

## 會停下來不做的情況（都是什麼都不改）

- 名單外又冒出新的有效訂單（例如今天查完之後又有人加單）→ 名單要重查。
- 要取消的單已經是「可取貨」或更後面的狀態（取消鈕只收 待確認／已確認／出貨中）。
- **0040 救回來時貨已經到店**：系統會直接把它推成「可取貨」，取消鈕取消不了 → 整份停下，這一張改人工處理。01 第④段會先告訴你會不會這樣。
- 0040 的客人在辣椒醬團還有別張進行中的訂單（一位客人一團只能一張，救回來會撞）。
- 用了儲值金、但會員帳號不是正常狀態（退不回去）。

## 萬一要撤回（05）

- 只還原「最近一次 02」取消的單，而且 02 之後**沒人再動過**那張單；有人動過就【停】、什麼都不改。
- 用的是後台「復原取消」那一支：單子回到已確認（貨已到店就直接可取貨）；**取消時退回的儲值金會重新扣回**，餘額不夠會停。
- ⛔ **辣椒醬 TF0001／0040 這一對不還原**：TF0001 是轉入單，系統本來就不准復原；只救 0040 的話，貨會回到原本那位客人，不是經國那位。要撤回請人工：0040 按「復原取消」，再重新轉單給經國。
- 老闆如果已經幫 0006 古華、0018 忠順補了 1 件（補的時候系統會開一張新單），那兩張就救不回來（一人一團一張），05 會先列出來再停。
- 取消時被系統一起放掉的「庫存減抵單」配貨不會自己長回來（取消鈕本來就這樣）。

## 不會動到的

派車單、庫存、採購單、請購單、月結、開團商品設定、會員通知。

## 本機實測（2026-10-28，臨時資料庫，跑完已刪）

用本機 PostgreSQL 18 建精簡版資料表，取消鈕、復原取消、儲值金退款／扣回、轉入單還原、權限檢查這幾支**從程式碼紀錄逐字切出來**載入（取貨閘門用假的代替）。
- 正常流程：01 全部 ✅ → 02 取消 74 張（73＋0040）、退儲值金 1 張 → 04 全部 ✅ → 02 重貼顯示「已經做過」→ 05 還原 72 張、儲值金扣回、TF0001／0040 留著 → 05 重貼顯示「已經還原過」。
- 會停的情況都試過：操作人空白／不是總部、0040 貨已到店、名單外有新單、0040 客人另有一張單、有一張是可取貨 → 都是【停】而且什麼都沒改。
- 已經有人手動按掉 1 張＋TF0001 時，02 會跳過那 2 張、照樣把 0040 取消。
- 部分轉出的情況（0040 的品項被搬到 TF0001）也試過：結果一樣是 34 件。
- 測不到的：正式系統其他欄位、其他觸發器、真正的取貨閘門。

## 0. 全域設定

| 項目 | 位置 | 內容 |
|---|---|---|
| PostgREST max rows | `supabase/config.toml:18` | `max_rows = 1000` |

所有透過 PostgREST 的查詢（含 view、RPC 回 SETOF）若無顯式分頁，皆會在 1000 列截斷。**所有下方風險的根因。**

## 1. HIGH 風險（資料正確性受影響）

### #1 — 訂單稽核日誌無 limit
- **狀態**：🔴 PENDING
- **檔案**：`apps/admin/src/components/OrderAuditDrawer.tsx:71-76`
- **現況**：
  ```ts
  .from("customer_order_audit_log")
  .select(...)
  .eq("order_id", orderId)
  .order("created_at", { ascending: false })
  // 無 .limit() / .range()
  ```
- **風險**：單筆訂單若編輯次數 >1000，稽核軌跡顯示不完整。**合規風險**。
- **修法**：採模式 A（cursor 分頁 + load more）。新增 `before_id` 參數，UI 加「載入更多」。
- **驗證**：種子腳本 `scripts/audit-pagination/test-01-audit-log.mjs`，建立 1100 筆 audit 紀錄，驗證能完整載入。

### #2 — HQ Inbox 缺貨彙整 limit(20000)
- **狀態**：🔴 PENDING
- **檔案**：`apps/admin/src/app/(protected)/hq/inbox/page.tsx:534-549`
- **現況**：`v_order_shortage` 用 `.limit(20000)`，前端 reduce 做缺貨摘要。
- **風險**：>20K 列時隱藏缺貨，且前端 reduce 違反 §4.1（金額/數量類不可前端聚合）。
- **修法**：建立 `rpc_shortage_summary` (JSONB 模式 B)，SQL 端完成聚合。
- **驗證**：種子腳本插入 21000 筆缺貨記錄，驗證摘要金額/數量正確。

### #3 — Exception 面板缺貨資料 limit(20000)

- **風險**：例外面板缺貨顯示不完整。

### #11 — Campaign detail items 無 limit
- **狀態**：🔴 PENDING
- **檔案**：`supabase/functions/liff-api/index.ts:409-414` (`getCampaignDetail`)
- **現況**：
  ```ts
  sb.from("campaign_items").select(...)
    .eq("campaign_id", campaignId)
    .order("sort_order");
  // 無 limit，倚賴 PostgREST 1000 兜底
  ```
- **風險**：單一團 SKU >1000 時商品消失。
- **修法**：併入 #12 的 `rpc_campaign_detail_with_counts`（模式 B JSONB）。
- **金額/數量類**：✅（涉及 `unit_price`, `cap_qty`）

### #12 — Campaign detail ordered_qty 聚合無 limit ⚠️
- **狀態**：🔴 PENDING
- **檔案**：`supabase/functions/liff-api/index.ts:429-435`
- **現況**：
  ```ts
  sb.from("customer_order_items").select(...)
    .eq("customer_orders.campaign_id", campaignId)
    // 無 limit，後續做 itemOrderedMap 聚合
  ```
- **風險**：**團 >1000 訂單行時「已訂數量」被低估**，導致 cap_qty 計算錯誤，**會員可能下到超賣的單**。
- **修法**：必須改 SQL 端聚合，使用 `rpc_campaign_detail_with_counts`（模式 B）。**禁止**前端 reduce。
- **金額/數量類**：✅ 違反 §4.1，**首批最高優先**。

### #13 — rpc_member_campaign_order_counts 無分頁 ⚠️
- **狀態**：🔴 PENDING
- **檔案**：
  - SQL: `supabase/migrations/20260616000010_rpc_member_campaign_order_counts.sql:13-38`
  - 呼叫: `supabase/functions/liff-api/index.ts:337-344`
- **現況**：RPC `GROUP BY campaign_id`，回 `SETOF`，仍受 1000 列限制。
- **風險**：>1000 個團時熱銷/近期排序失準。**訂單數量類**。
- **修法**：改回 `RETURNS jsonb`（模式 B），單列回傳 `{ campaign_id: count }` map。
- **金額/數量類**：✅

### #14 — listActiveCampaigns 倚賴 PostgREST 1000 兜底 ⚠️
- **狀態**：🔴 PENDING
- **檔案**：`supabase/functions/liff-api/index.ts:296-311`
- **現況**：刻意無 `.limit()`，註解寫明「PostgREST 仍有 db-max-rows=1000 兜底」。
- **風險**：開團數突破 1000 時整批靜默消失。違反 §3 B2（依賴 PostgREST 兜底）。
- **修法**：改 RPC `rpc_list_active_campaigns` 回 JSONB（模式 B），或加 cursor 分頁。

### #15 — rpc_list_staff 無分頁
- **狀態**：🔴 PENDING
- **檔案**：`supabase/migrations/20260613000150_staff_permissions.sql:38-86`
- **現況**：`RETURNS TABLE`，無分頁參數。
- **風險**：員工數 >1000 時管理頁不完整。
- **修法**：加 `p_page`, `p_page_size` 參數，或改 JSONB 單列回傳。

### #16 — v_hq_inbox view 無內建 LIMIT
- **狀態**：🔴 PENDING
- **檔案**：`supabase/migrations/20260608000010_hq_inbox_view_and_counts.sql:34-99`
- **現況**：4 來源 UNION view，本身無 LIMIT。已有 `rpc_hq_inbox_keys`（正確分頁）但呼叫端未必都走它。
- **風險**：若前端有人直接 `sb.from("v_hq_inbox").select("*")`，截斷。
- **修法**：
  1. 在 view 加 `COMMENT ON VIEW v_hq_inbox IS '⚠️ DO NOT query directly via PostgREST. Use rpc_hq_inbox_keys() instead.'`
  2. grep 全 repo 確保沒有人直接查 view。
- **驗證**：CI 加 lint 規則禁止 `from("v_hq_inbox")` 字串出現。
